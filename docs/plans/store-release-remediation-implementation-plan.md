## 0. نطاق التنفيذ الذي أستطيع إنجازه

هذه الخطة تخص الإصلاحات التي يستطيع Codex تنفيذها والتحقق منها داخل المشروع. يبدأ
التنفيذ محليًا على Windows، وتُستكمل الاختبارات التي تحتاج خدمات خارجية أو أجهزة
أصلية فور توفير الوصول المطلوب. لا يشمل التنفيذ شراء حسابات، اعتماد نص قانوني بدل
المالك، استخدام بيانات عملاء حقيقية، أو رفع إصدار Production دون موافقة صريحة.

| المسار | ما سأنفذه | ما يوقف الإغلاق النهائي فقط |
|---|---|---|
| الاختبارات | إصلاح Fixtures وDI والتوقعات القديمة، إضافة اختبارات Regression، وتسجيل Baseline قابل للإعادة | لا شيء لبدء العمل المحلي |
| Supabase والأمان | إزالة السر من الشجرة الحالية، إنشاء Migrations أمامية آمنة، حماية الأدوار، وإعادة بناء عقد إنشاء الطلب | تدوير المفتاح، الوصول للمشروع التجريبي، وبيانات حسابي عميل ومدير |
| السلة والدفع | إصلاح الخيارات والكوبون ورسوم التوصيل والوقت المجدول ومنع تكرار الطلب | اختبار حي على Supabase التجريبي |
| الحساب والإشعارات | إكمال التأكيد والاستعادة والعناوين والبصمة والتنقل من الإشعارات وLogout | إعدادات Firebase/APNs واختبار أجهزة حقيقية |
| الإدارة | إصلاح نتائج تحديث الطلب والدفع والتقارير وCSV والطباعة والتقييمات | قرار إبقاء التقييمات العامة وتوفر الطابعة/iPad عند الاختبار النهائي |
| الخصوصية | تنفيذ حذف الحساب وصفحة الحذف وروابط الخصوصية والدعم والإبلاغ والحظر وجرد البيانات | اعتماد سياسة الاحتفاظ والنصوص القانونية وبيانات الدعم |
| Android | إصلاح الموارد وRelease Signing configuration والصلاحيات وبناء AAB وفحص API 36 و16KB وإضافة CI | Upload Key والأيقونة النهائية وحساب Play Console وأجهزة الاختبار |
| iOS | تجهيز ملفات Firebase وInfo.plist وEntitlements وPrivacy Manifests وmacOS CI | Mac وXcode 26+ والتوقيع وiPhone/iPad |
| مواد المتجر | إعداد مسودات الوصف وRelease Notes وتعليمات المراجع وقوائم Data Safety وApp Privacy | اعتماد المالك والدول والفئة العمرية ثم الإرسال الفعلي |

### ترتيب الأولويات التنفيذي

1. **P0 — احتواء أمني:** السر المكشوف، صلاحيات الأدوار، وسيادة الخادم على الطلب.
2. **P1 — صحة الوظائف:** السلة وCheckout والحساب والإشعارات وعمليات الإدارة.
3. **P1 — قابلية الإصدار:** Android AAB ثم تجهيز iOS وCI.
4. **P1 — التزام المتاجر:** الحذف والخصوصية والمحتوى وبيانات المراجعة.
5. **P2/P3 — الجودة:** الأداء وRTL والإتاحة والتنظيف التجميلي.

لا تنتقل الخطة إلى الرفع التجريبي قبل إغلاق كل P0 وP1 القابلة للتنفيذ محليًا.
ولا يُعلن Google Play أو App Store جاهزًا إذا ظل اختبار إلزامي للمنصة متوقفًا.

## 1. قاعدة استخدام Skills

استخدام الـSkills جزء إلزامي من الخطة، وليس اقتراحًا. قبل بداية كل مرحلة سأفتح ملفات `SKILL.md` المذكورة في جدول المرحلة وأتبع قواعدها. إذا تعذر تحميل Skill مطلوبة، تتوقف المرحلة حتى يتضح السبب. تعليمات المشروع وقرارات المالك تتقدم على أي نص عام داخل Skill.

### Skills الأساسية طوال التنفيذ

| Skill | استخدامها |
|---|---|
| `implement-feature` | إدارة دورة التنفيذ من الخطة إلى الكود والتحقق |
| `common-git-collaboration` | فرع `codex/` مستقل، تغييرات صغيرة، وعدم لمس ملفات المستخدم |
| `common-tdd` | اختبار فاشل أولًا ثم أقل إصلاح ثم Refactor |
| `flutter-testing` | Fixtures وBLoC/Widget/Integration tests ونمط Robots عند تطوير اختبارات UI |
| `dart-tooling` | التنسيق والتحليل وتوليد الكود عند الحاجة |
| `flutter-layer-based-clean-architecture` | الحفاظ على اتجاه الاعتماد بين الطبقات |
| `flutter-error-handling` | عدم إسقاط `Either<Failure, T>` وإظهار حالات الفشل الصحيحة |
| `common-feedback-reporter` | مراجعة الالتزام بالـSkills قبل إنهاء كل مرحلة |

## 2. استراتيجية التنفيذ العامة

1. إنشاء فرع `codex/store-release-readiness` عند بدء التنفيذ الفعلي، بعد فحص حالة Git وحماية الملفات غير المتتبعة.
2. العمل على مرحلة واحدة فقط في كل وقت؛ لا تُخلط تغييرات الأمان مع تحسينات الشكل.
3. لكل عيب: اختبار RED يثبت السلوك، ثم إصلاح GREEN محدود، ثم Refactor مع بقاء الاختبارات ناجحة.
4. تشغيل الاختبارات الأقرب للتغيير أولًا، ثم `flutter analyze` والاختبارات الكاملة في نهاية المرحلة.
5. أي Migration جديدة تُراجع كنص أولًا، ثم تُجرب على مشروع Supabase تجريبي فقط قبل تطبيقها على هدف آخر.
6. لا يُستخدم المفتاح الموجود في المصدر، ولا يُطبع أو يُنسخ إلى أداة أو Log.
7. لا يعتبر نجاح Web أو Emulator بديلًا عن بناء واختبار المنصة الأصلية.

## 3. المراحل

### المرحلة 0 — تثبيت بيئة إصلاح موثوقة

**Skills:** `implement-feature`, `common-git-collaboration`, `common-tdd`, `flutter-testing`, `dart-tooling`.

**العمل:**

- حفظ Snapshot لحالة Git والـCommit والملفات غير المتتبعة قبل أي تعديل.
- إنشاء فرع العمل دون نسخ أسرار أو مفاتيح.
- إصلاح 23 مشكلة Fixture/DI و5 Assertions قديمة في الاختبارات، مع عدم تغيير متطلبات التطبيق لإرضاء اختبار قديم.
- نقل بيانات دخول Integration إلى `String.fromEnvironment` دون قيم افتراضية.
- إضافة Helpers مشتركة لـGetIt وBLoC بدل تكرار Mocks محلية.
- تثبيت أو نقل الاختبارات الأربعة المركزة إلى أماكنها الطبيعية داخل الاختبارات الحالية.
- توثيق خط الأساس: Analyzer، Format، Tests، Coverage، وبناء Android المعروف بالفشل.

**بوابة الخروج:** الاختبارات الحالية تنفذ فعلًا دون أخطاء Setup؛ تظل اختبارات العيوب الجديدة حمراء للأسباب الصحيحة؛ لا توجد بيانات دخول داخل الاختبارات.

### المرحلة 1 — احتواء الأسرار وحماية الهوية وعقد الطلب

**Skills:** `flutter-security`, `common-security-audit`, `auth-review`, `common-owasp`, `flutter-layer-based-clean-architecture`, `common-tdd`, `flutter-testing`.

**العمل:**

- إزالة القيمة المرتفعة الصلاحيات من الشجرة الحالية وإيقاف الاعتماد على جدول إعدادات يقرأه العميل.
- إضافة Migration أمامية تقيد أو تلغي سياسة `app_config` وتحوّل الإشعارات إلى Secret server-side معتمد.
- إعداد تعليمات منفصلة للمالك لتدوير المفتاح وتنظيف Git history؛ لا أنفذ إعادة كتابة التاريخ دون موافقة.
- جعل دور التسجيل `customer` على الخادم، وتقييد أعمدة تعديل الملف الشخصي، وإضافة فحص دور إداري محمي دون RLS recursion.
- تصميم وتنفيذ `create_order` جديد: `auth.uid()`، حالة ابتدائية خادمية، أسعار وخيارات ورسوم موثوقة، كوبون ذري، ومفتاح Idempotency.
- إلغاء صلاحيات `PUBLIC` غير المطلوبة وتثبيت `search_path` للدوال ذات الصلاحيات.
- توحيد حالات الدفع بين SQL وDart وإنشاء Migration قابلة للتطبيق والترقية.
- نقل جلسة Supabase إلى تخزين آمن بخطة ترحيل ومسح للقيم القديمة.
- إنشاء اختبارات سلبية لمجهول وعميل A وعميل B ومدير، وتزوير السعر والهوية والدور والكوبون.

**تغييرات العقد الموثقة مسبقًا:** إضافة مفتاح إرسال للطلب، إعادة حساب الحقول المالية على الخادم، ودالة دور محمية. تُحدّث DTOs وRepositories بصورة متوافقة في نفس المرحلة.

**بوابة الخروج:** لا Secret في الشجرة الحالية؛ اختبارات العقود السلبية تنجح على المشروع التجريبي؛ الدور لا يتغير من العميل؛ الطلب المزور يُرفض؛ التكرار يعيد نفس الطلب؛ الكوبون لا يستهلك إلا مع الطلب الناجح. تدوير المفتاح الفعلي يبقى بوابة مالك مستقلة.

### المرحلة 2 — صحة السلة وCheckout والطلب

**Skills:** `common-tdd`, `flutter-testing`, `flutter-error-handling`, `dart-best-practices`, `flutter-feature-based-clean-architecture`, `common-debugging`.

**العمل:**

- أخذ نسخة غير قابلة للتعديل من خيارات المنتج عند إضافته للسلة.
- إصلاح `copyWith` بحيث يفرق بين «لم يُمرر» و«امسح القيمة» للكوبون والمنطقة.
- اشتقاق العنوان والمنطقة والرسوم من نوع الطلب الحالي، ومسح حقول التوصيل عند الاستلام أو داخل المطعم.
- فرض الخيارات الإجبارية والتوفر والحد الأدنى والوقت المجدول الصالح قبل الإرسال، مع بقاء الخادم المرجع النهائي.
- الاحتفاظ بمفتاح Idempotency خلال فشل الشبكة والمحاولة اللاحقة.
- توحيد الإجمالي المعروض والإجمالي الذي يرسله Repository.
- إضافة اختبارات Offline/Timeout، النقر المتكرر، السعر القديم، الكوبون المتزامن، وتغيير نوع الطلب.

**بوابة الخروج:** الاختبارات الأربعة المركزة خضراء؛ لا يتغير عنصر سابق بتعديل شاشة المنتج؛ لا تبقى رسوم أو معرفات قديمة؛ إعادة الإرسال لا تكرر الطلب.

### المرحلة 3 — الحساب والاستعادة والعناوين والإشعارات

**Skills:** `auth-review`, `flutter-security`, `flutter-navigation`, `flutter-notifications`, `flutter-error-handling`, `flutter-testing`.

**العمل:**

- تنفيذ حالة انتظار تأكيد البريد وإعادة الإرسال والعودة الصحيحة للتطبيق.
- تنفيذ استعادة كلمة المرور كاملة: Deep Link، جلسة Recovery، نموذج كلمة جديدة، نجاح وفشل وخروج واضح.
- إصلاح حفظ العنوان بحيث يبقى النموذج والقيم عند الفشل.
- جعل موافقة البصمة مرتبطة بالحساب الحالي وتنظيف بياناتها عند الخروج أو تبديل الحساب.
- إعادة بناء توجيه الإشعار باستخدام معرف الطلب وحالة تحميل وصلاحية، دون الاعتماد الإجباري على `extra`.
- صف إشعار التشغيل البارد حتى يصبح Auth وRouter جاهزين، ودعم وصول إشعار ثانٍ لنفس الشاشة.
- مراجعة Logout وإلغاء Device Token والاشتراكات.

**بوابة الخروج:** اختبارات التسجيل المؤكد والاستعادة والعنوان وتبديل الحساب والإشعارات الباردة/الدافئة تنجح، ولا يوجد Crash أو نجاح كاذب أو تسريب بيانات اعتماد بين حسابين.

### المرحلة 4 — عمليات الإدارة والتقارير والطباعة والمحتوى

**Skills:** `flutter-error-handling`, `flutter-testing`, `common-tdd`, `common-performance-engineering`, `common-mobile-ux-core`.

**العمل:**

- معالجة `Either` في تحديث حالة الطلب والدفع وإظهار النجاح بعد الحفظ فقط.
- إصلاح نطاق التقارير إلى `[بداية اليوم الأول، بداية اليوم التالي)` بتوقيت العمل.
- انتظار نتيجة تصدير CSV وإضافة موضع مشاركة iPad ومعالجة الإلغاء والفشل.
- إعادة تصميم حدود خدمة الطابعة دون Context مخزن، والتحقق من نتيجة الاتصال والطباعة.
- إكمال المفضلة أو إخفاؤها من الإصدار حسب قرار المنتج.
- مراجعة التقارير والاستعلامات الثقيلة وتسجيل زمنها على بيانات تجريبية.
- إصلاح عرض التقييمات عبر Projection آمن لا يكشف عناصر طلبات خاصة.

**بوابة الخروج:** لا تعرض الإدارة نجاحًا عند الرفض؛ التقارير وCSV متطابقان حتى آخر اليوم؛ المشاركة تعمل على iPad عند توفره؛ الطباعة لا تدعي نجاحًا كاذبًا.

### المرحلة 5 — الخصوصية والحذف وإدارة التقييمات

**Skills:** `flutter-security`, `common-security-standards`, `common-product-requirements`, `flutter-testing`, `common-documentation`.

**العمل:**

- تنفيذ واجهة حذف الحساب وعقد خادم موثق وآمن وإلغاء الجلسات وTokens.
- تطبيق سياسة الاحتفاظ المعتمدة: حذف أو إخفاء البيانات الشخصية مع الحفاظ فقط على السجلات المطلوبة قانونيًا.
- إنشاء صفحة ويب عامة لطلب حذف حساب Google وربطها من المتجر والتطبيق.
- ربط الخصوصية والشروط والدعم داخل التطبيق والموقع.
- إضافة الإبلاغ والحظر وقائمة Moderation وسجل تدقيق للإجراءات.
- إعداد مصفوفة بيانات فعلية لـGoogle Data Safety وApple App Privacy تشمل Supabase وFirebase وSentry.

**بوابة المالك:** اعتماد نصوص الخصوصية والاحتفاظ والدعم وقرار إبقاء التعليقات العامة.

**بوابة الخروج:** حذف العميل لحسابه لا يؤثر على حساب غيره، وتتوقف الجلسة، وتطابق البيانات المتبقية السياسة؛ روابط السياسات والحذف عامة وتعمل؛ الإبلاغ والحظر والمراجعة قابلة للتنفيذ.

### المرحلة 6 — Android Release

**Skills:** `flutter-devops`, `flutter-cicd`, `flutter-security`, `dart-tooling`, `common-mobile-visual-testing`, `common-performance-engineering`.

**العمل:**

- تصحيح قواعد `.gitignore` وتتبع الأيقونات والصور الضرورية أو توليدها من مدخل معتمد.
- إعداد Release Signing عبر متغيرات/Secrets، دون Commit لمفتاح أو كلمة مرور.
- إزالة صلاحيات Manifest غير المستخدمة بعد إثبات مصدر كل Permission.
- بناء AAB من Clone نظيف مع `--obfuscate` و`--split-debug-info` وحفظ Symbols بصورة خاصة.
- فحص Package ID والإصدار والشهادة وTarget API والـManifest والمكتبات الأصلية ومحاذاة 16KB.
- اختبار API الأدنى والحالي وبيئة 16KB، مع RTL والنص الكبير والإشعارات والبصمة والكاميرا وWhatsApp.
- إضافة Android Release job محدد المهلة إلى CI ورفع Artifact داخلي فقط.

**بوابة المالك:** توفير Upload Key بطريقة آمنة وحساب Play App Signing والأيقونة النهائية المعتمدة.

**بوابة الخروج:** AAB موقع قابل لإعادة الإنتاج، ينجح فحص Play/Internal Testing ومصفوفة Android، ولا توجد Permissions غير مبررة.

### المرحلة 7 — تجهيز iOS ثم التحقق على Mac

**Skills:** `xcode-project-setup`, `flutter-notifications`, `flutter-security`, `flutter-cicd`, `common-mobile-visual-testing`.

**العمل المحلي الممكن على Windows:**

- تجهيز ملفات Firebase الصحيحة كمدخل بيئي غير سري، وأوصاف الكاميرا والصور، وEntitlements وCapabilities المطلوبة.
- تحديث `connectivity_plus` و`share_plus` تحديثًا موجهًا إلى إصدارات متوافقة مع Privacy Manifests، مع اختبارات رجوع.
- مراجعة Deployment Target وBundle ID وiPad layouts والمشاركة والطباعة.
- إعداد خطوات CI على macOS دون وضع شهادات داخل المشروع.

**العمل عند توفر Mac:**

- تنفيذ `swift --version` أولًا وفق Skill؛ لا Ruby ولا تعديل نصي عشوائي لـ`.pbxproj`.
- استخدام أدوات Swift الآمنة أو Xcode لربط الموارد، ثم فحص `CODE_SIGN_ENTITLEMENTS` وFirebase والـPrivacy Report.
- بناء Archive باستخدام Xcode 26+ وiOS 26 SDK+، وفحص التوقيع والـCapabilities وملفات الخصوصية.
- اختبار iPhone وiPad: Push والكاميرا والصور والمشاركة والدوران وSplit View والنص الكبير وVoiceOver.

**بوابة المالك:** Mac وحساب Apple Signing والأجهزة وملف Firebase الصحيح.  
**بوابة الخروج:** Archive يمر App Store Validation واختبارات iPhone/iPad؛ لا يمكن إغلاق المرحلة على Windows وحده.

### المرحلة 8 — CI والاختبار النهائي ومواد المتجر

**Skills:** `flutter-cicd`, `flutter-testing`, `common-mobile-visual-testing`, `common-performance-engineering`, `common-store-changelog`, `requesting-code-review`.

**العمل:**

- ترتيب CI: Format → Analyze → Unit/Widget → Coverage → Android AAB → iOS Archive على macOS.
- وضع `timeout-minutes` وCache مضبوط وArtifacts خاصة دون أسرار.
- تشغيل Integration على مشروع تجريبي بحسابين ومدير، واختبار Offline والتزامن وRealtime والاستئناف.
- قياس Startup والتمرير والصور والتقارير على أجهزة تمثيلية وتوثيق الأرقام الفعلية.
- تنفيذ مراجعة RTL وإتاحة الوصول وحالات التحميل والخطأ في المسارات الحرجة.
- إعداد وصف المتجر وRelease Notes وقائمة Data Safety/App Privacy وتعليمات المراجع دون دفع حقيقي.
- مراجعة نهائية مستقلة للكود والـDiff والأسرار والحزم.

**بوابة الخروج:** صفر P0/P1 مفتوحة، جميع الاختبارات والـBuilds ناجحة، Supabase المستهدف متحقق، ومتطلبات كل متجر مكتملة بصورة مستقلة.

## 4. ترتيب الدمج المقترح

لا يتم دمج كل العمل في Commit واحد. التقسيم المقترح:

1. `test: repair release-readiness test harness`
2. `security: contain privileged configuration exposure`
3. `security: enforce server-authoritative order creation`
4. `fix: make cart and checkout state consistent`
5. `fix: surface admin and account operation failures`
6. `feat: add account deletion and review moderation`
7. `build(android): configure reproducible signed release`
8. `build(ios): complete native resources and privacy setup`
9. `ci: add native release verification gates`
10. `docs: add store disclosures and reviewer instructions`

كل وحدة تُراجع وتُختبر قبل الانتقال لما بعدها. اسم الفرع يستخدم بادئة المشروع المطلوبة `codex/`.

## 5. سياسة التوقف والرجوع

- إذا فشلت Migration على المشروع التجريبي، لا تُطبق على أي مشروع آخر ويُحفظ Log معقم.
- إذا تغير عقد API، يجب تحديث العميل والخادم والاختبارات في نفس الوحدة قبل الدمج.
- إذا تسببت ترقية مكتبة في Regression، تُرجع الترقية وحدها ويُبحث عن إصدار متوافق آخر.
- لا يُرفع أي Build إلى Production؛ Internal Testing/TestFlight أولًا ثم موافقة المالك.
- لا يُعلن المتجر جاهزًا بوجود P0/P1 أو فحص إلزامي متوقف.
